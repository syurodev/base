# Event storage và recovery

Trạng thái: foundation contract v0.5. V1 chốt semantics bên dưới; DDL/migration và protected-payload implementation vẫn cần storage/security review. [Event catalog](/dev-kit/core-harness/event-catalog) liệt kê các facts có thể xuất hiện.

## 1. Source of truth và projections

Run event stream là nguồn gốc của execution facts cho native runtime: run/step, model/tool attempts, blockers, stop intent, timers, active-time windows và budget observations. Các projection gồm current control state, derived lifecycle/phase, execution intents, timer index, command receipts và **canonical transcript native**.

Projection được cập nhật cùng transaction với append. Execution intent là view/projection suy ra từ events, không có API ghi intent độc lập. Rebuild dựng dữ liệu, không dispatch. Các bảng domain về approval, task, Git ownership, peer outbox và vault vẫn thuộc owner cũ; event chỉ ghi references/observations có provenance.

Không thêm persisted snapshots v1. Stream theo run và current projections đã đủ cho baseline; nếu run dài cần phân đoạn/history budgets hoặc snapshot sau này phải có evidence và quyết định riêng. UI “snapshot” trong tài liệu chỉ là consistent read của projection kèm sequence, không phải event-sourcing snapshot được lưu bền vững.

## 2. Một quyền ghi stream

**Chỉ session/run coordinator của owner được append execution stream.** Với run đã admitted, coordinator phải giữ admission token hiện tại. Với run còn Queued, chỉ allowlist pre-admission commands (accept/queue metadata/cancel, purpose hợp lệ của TimerFired, metadata-only close) được ghi bằng queue-owner authority, expected run revision và session/queue revision; chúng không dispatch và không chiếm active admission. Repository là transaction adapter của coordinator, không là một writer/scheduler độc lập. Model/tool workers, timer scheduler, interaction bridge và UI chỉ gửi command/observation vào coordinator; không claim SQL row, append event hoặc sửa transcript trực tiếp.

Dispatch protocol:

1. Coordinator đọc facts/revision, kiểm tra wait dependencies/interruption causes, stop intent, budget và facts từ owner; giữ chỗ worker capacity trước transaction, chưa chạy effect. Không có slot thì chờ local capacity, không tạo DispatchStarted hoặc Cancelled.
2. Trong transaction có fence, append `ModelDispatchStarted` hoặc `ToolDispatchStarted`; projection intent chuyển `dispatching`, cùng admission/executor token, attempt ID và budget reservation (cả model lẫn tool).
3. Sau xác nhận commit, coordinator giao work item vào slot bounded worker channel đã giữ đúng một lần trong incarnation đó. Worker kiểm tra cancellation/token hiện hành và gateway khi thực thi.
4. Worker trả observation; coordinator validate identity, terminal evidence và expected state rồi append completion/result transaction.

Không re-enqueue các intents đã `dispatching` khi restart. Crash giữa bước 2 và 3 không chứng minh đã ra ngoài; vì mất handoff evidence nên xử lý bảo thủ như unknown, hoặc dùng evidence cụ thể từ owner để đối soát. Channel đầy không phải cancellation: slot phải được reserve trước commit. Nếu coordinator còn sống chứng minh chưa handoff khi có stop thật, có thể ghi cancellation pre-handoff với stop provenance; lỗi handoff nội bộ có typed host-failure evidence, không giả user cancel; không suy rộng bằng chứng memory này qua restart.

Commit thất bại hoặc stop trước dispatch trả worker slot; commit unknown giữ slot đến khi read-back rõ, hoặc kết thúc host mà không handoff. Slot chỉ là memory capacity reservation, không là persisted worker claim.

Commit unknown phải read-back bằng command/event identity trước giao worker. Nếu chưa xác định được, dừng dispatch; không tạo command ID mới để thử lại. Observation cũ có thể được current coordinator thu thập làm reconciliation evidence, nhưng không cho stale worker trực tiếp ghi đè state mới.

## 3. Session admission và fencing

Trước khi tạo `ownerIncarnation`, mở execution writer, re-arm scheduler hoặc acquire run, mọi host MUST giữ **cùng OS-backed exclusive lock trên canonical data directory**, độc lập Wails. Chỉ host lifecycle owner đã lấy lock được tạo incarnation mới. Host thứ hai bị từ chối trong khi owner còn giữ lock; không suy ra process chết từ PID, timestamp, timeout hoặc việc không có heartbeat. Không unlink lock file để vượt lock. Khóa giữ đến khi đóng writers/scheduler/dispatch ingress; OS release sau crash cho host mới acquire rồi recovery. Mất lock thì fail closed, không lấy admission token để giành run. Lock không chứng minh subprocess/external operation của host cũ đã dừng. Lock primitive, canonical path/alias handling và supported filesystem semantics phải được chốt/test ở G-02/G-03; remote/shared-data-directory failover ngoài v1.

V1 chọn **một admission row có fencing token cho mỗi session**, thuộc session/execution owner hiện hữu; không thêm session event stream thứ hai. Logical fields: `sessionID`, `activeRunID`, `ownerIncarnation`, monotonic `admissionToken`, `revision`, cùng context-control fields bên dưới. Đây là control ownership row, không là managed writer lease hoặc bằng chứng process dừng.

- Nhận run mới có thể tạo `RunAccepted` và giữ `Queued`, chưa chiếm session. Queue/pause policy hiện hữu vẫn quyết định chọn run.
- Admission transaction kiểm tra `activeRunID` còn trống hoặc recovery đúng cùng run, session còn hợp lệ và domain ownership guards cho phép; CAS admission row, tăng token và append `RunAdmitted`/`RunOwnershipAcquired` cùng projection trong transaction của owner.
- Sau admission, mọi append/dispatch authorization/completion phải khớp active run, current owner incarnation và admission token. Cạnh tranh admission chỉ một bên commit. Pre-admission accept/cancel dùng queue-owner fence, không đòi Queued run là active run và không được sửa admission của run khác.
- Chỉ incarnation được tạo sau exclusive lock acquisition mới được recovery; session owner xác thực incarnation theo host-bound authority, không nhận ID do client tự chọn. Restart có thể lấy token mới để **phục hồi cùng active run**. Token cũ mất quyền ghi/dispatch; không tự clear active run hoặc chạy một run khác chỉ vì lease/time đã hết.
- `RunFinished` của run đã admitted có thể clear đúng active control admission của chính run đó trong cùng transaction. Finish/cancel một Queued run không được clear admission đang thuộc run khác. Managed writer/resource ownership là kiểm tra riêng; unknown exposure hoặc process chưa được chứng minh dừng vẫn có thể chặn run mới xung đột.
- Session close/parent close và các change có ảnh hưởng authority cần fence ở owner boundary phù hợp; kiểm tra row admission không thay current capability/workspace checks.

Coordinator serialization giảm tranh chấp trong process; CAS và token vẫn là correctness boundary. Một external process không tuân thủ token không bị dừng bằng fencing; sandbox/owning service phải tiếp tục quản lý nó.

### Context control cùng admission row

Session/execution owner lưu context state **trên admission row**, không thêm session stream hoặc boolean độc lập trong UI: contextEpoch, contextStartRunID, contextRevision, contextRequirement (none/revalidation_required/fresh_required), contextCauseRunID và reference event đã quyết định nó. Các fields là control projection, không chứa transcript/args. RunClosureConfirmed + RunFinished của run đã admitted trong current context epoch cập nhật row cùng transaction clear admission: missing/corrupt payload bắt buộc fresh_required; vault_locked chỉ revalidation_required. Close một Queued run chưa materialize input không đổi context requirement của history đang chạy. Yêu cầu fresh đã có không được hạ thành revalidation chỉ vì một close sau nói vault_locked. Nếu tiếp tục context phát hiện mất/hỏng payload thì từ chối có kiểu, giữ requirement chưa giải quyết để user chọn fresh; không tự sửa history.

Trusted user gửi SelectRunContext với queued target run, mode fresh/continue, expected run/session-queue/context revisions và preview context boundary. Guard: không có active run khác, queue/pause cho admit, current scope/ownership hợp lệ. Selection và RunAdmitted MUST commit **cùng transaction**: append ContextBoundarySelected vào stream của target run, cập nhật context fields + admission row, project input. Không thể chọn boundary rồi để run khác lén admit trước target. mode=fresh tăng epoch và đặt contextStartRunID=target; mode=continue giữ epoch/start, chỉ cho phép khi requirement không phải fresh_required và owner đã unlock/mở/validate đầy đủ context cùng canonical pairs. Cả hai chỉ clear requirement khi transaction thành công; không có lệnh set flag trực tiếp. AdmitRun thông thường bị chặn khi requirement chưa giải quyết; fresh khi vault còn khóa cũng phải chờ unlock để materialize input theo contract RunAdmitted.

ContextBoundarySelected ghi old/new contextRevision/epoch, startRunID, mode, actor, validation evidence refs và previous deciding-event ref. Nó ở **run stream**, không là session event stream. Context-control projection rebuild fold các deciding events của session theo contextRevision (epoch/revision 0 khi chưa có history; RunAdmitted đầu tiên ghi contextStartRunID và context revision khởi tạo trong cùng transaction), kiểm tra predecessor chain và gap/conflict; không dựa thứ tự UUID/timestamp hoặc quét tùy ý giữa run streams. RunClosureConfirmed cũng ghi previous/new contextRevision và resulting requirement; retention/deletion MUST giữ các deciding control events hoặc từ chối tiếp tục context khi không thể rebuild. Migration/DDL và rebuild proof thuộc G-03.

Canonical transcript projection giữ nguyên mọi epoch cũ và gắn epoch/contextStartRunID của run khi admit. Context builder cho run mới chỉ lấy canonical input/selected responses/tool results của **cùng epoch từ startRunID theo admission order**, cộng input hiện tại và system/tool declarations hiện hành theo pinned config; không lấy prompt/summary/attachment/payload refs từ epoch cũ qua compaction hoặc fallback. Fresh loại toàn bộ hội thoại trước boundary khỏi provider context, không chỉ entry bị hỏng; không thêm model-facing summary bịa về nội dung mất. UI vẫn có thể hiển thị metadata/history cũ với availability rõ ràng. Continue sau vault_locked giữ conversation và fixed terminal dispositions của run đã đóng khi tất cả content cần thiết còn đọc/validate được; không resume run đã finished hoặc tự replay effect. User muốn tái dùng tài liệu từ epoch cũ phải attach qua input có scope mới, không implicit carry-over.

## 4. Event envelope và provenance

| Field logic | Semantics |
| --- | --- |
| `eventID`, `runID`, `sequence` | Event identity và total commit order trong run |
| `eventType`, `schemaVersion`, `executionProtocolVersion` | Decode và semantics tương thích |
| `commandID`, `causationID`, `correlationID` | Dedup và quan hệ nhân quả; command có thể tạo một event batch |
| `sessionID`, `stepID`, `invocationID`, `attemptID` | Typed references phù hợp loại event |
| `writerIncarnation`, `admissionToken` / `queueRevision` | Quyền coordinator ghi event hiện tại; admission token bắt buộc sau admit, pre-admission dùng queue-owner revision |
| `executorIncarnation`, `attemptFence` | Attempt đang được mô tả; có thể là attempt trước restart khi đối soát |
| `origin` | Typed initiator/provenance do trusted host xác lập |
| `recordedAt` | Trusted host observation time; sequence vẫn là ordering |
| `data`, `payloadRef` | Allowlisted control fields và protected immutable content refs |

`origin.kind` gồm `user`, `parent_session`, `session`, `model`, `worker`, `timer`, `recovery`, `system`. Kèm principal/session/adapter/timer reference khi áp dụng, ingress/trust classification, và initiating command reference. `model` nghĩa model-origin proposal, không phải principal có quyền. `timer`/`recovery` là host actor với correlation tới facts gốc, không giả làm user.

Host MUST tạo origin từ authenticated caller, bound worker channel hoặc owned scheduler; không copy một object origin do client/model tự nhận. Khi system thực thi thay một user request, giữ cả initiator reference và executor provenance; không gộp thành một actor giả. User/parent authority vẫn phải được service xác thực lúc command/execute.

Không có metadata tùy ý: raw prompt/args/query/stdout/error cause, request reason và secrets không nằm trong envelope/audit. Human reason nếu cần nằm ở protected payload ref. Public error codes giữ publication/redaction contract hiện hữu.

## 5. Transaction và dedup equality

Một transaction coordinator thực hiện:

1. Kiểm tra command receipt, run revision và session admission fence; pre-admission allowlist dùng queue-owner authority/session-queue revision thay vì active-run token.
2. Kiểm tra các owner conditions cần linearize trong cùng DB boundary; ngoài owner phải dùng receipt/reconciliation contract.
3. Append event batch; cập nhật invocation/control/intent/timer projections và **native transcript projection** từ cùng events.
4. Ghi command receipt; cập nhật admission row nếu đây là admit/recover/finish.

Không giữ transaction/lock khi gọi network, worker, interaction hoặc chờ người dùng. Publish cho client chỉ sau commit. Không có transaction xuyên mọi domain hoặc external API; receipt bridge phải mô tả ambiguity nếu domain commit rồi execution observation chưa commit.

V1 chọn **so sánh trực tiếp protected canonical input**, không thêm digest hoặc HMAC/KDF mới:

- Command body được validate thành typed canonical representation; codec phải quy định field order, default/omitted, number encoding và reject duplicate JSON keys/unknown fields. Không normalize tùy tiện string/query/path làm thay nghĩa.
- Lưu canonical content trong protected payload store với immutable ref. Receipt gắn command kind, authenticated principal, target và input ref.
- Khi trùng command ID, trusted host mở protected input cũ và so byte canonical input, kind, principal và target. Khớp thì trả receipt cũ; khác thì typed conflict, không side effect.
- Không so ciphertext vì encryption nonce có thể khác. Khi vault khóa và cần mở input để so, trả `vault_required`/wait; không mặc định hai nội dung bằng nhau. Metadata-only commands như cancel hoặc CloseRunWithoutPayload có thể dedup nếu đầy đủ fields được phép lưu và so trực tiếp mà không mở secret payload.
- Approval gắn immutable validated args ref cùng request/target/revision và check generation; owner xác minh exact canonical args khi execute. Không chỉ so tên tool hoặc ID do model gửi.

HMAC là phương án có thể review sau nếu equality reads thành bottleneck, nhưng cần crypto/key-lifecycle/security ADR riêng. Không để implementation tự chọn hash plaintext không khóa hoặc đưa fingerprint vào metadata công khai.

## 6. Native transcript là projection

`RunAdmitted` đưa accepted input ref vào transcript theo admission order. `ModelResponseRecorded` đưa đúng response được chọn vào canonical assistant message; `ToolResultRecorded`/known disposition đưa kết quả tương ứng vào đúng tool-call ID/source position. Tất cả được projected trong transaction append tương ứng, không ở callback riêng.

`StepCompleted` chỉ hợp lệ khi projection đủ model/tool pairs của step; stop/deny/refusal/abandon dùng synthetic result có code/provenance trung thực, không giả tool success. Partial stream là attempt draft ngoài canonical transcript; retry không trộn output cũ vào response mới.

Payload có thể là artifact ngoài DB nhưng reference chỉ được commit khi content đã finalize trong protected store. Orphan artifact sau crash có thể thu gom; dangling ref không được coi là response rỗng. Xóa payload theo retention làm context unavailable dù lifecycle metadata còn rebuild được.

Đây là contract của **native runtime tương lai**. Không chuyển vendor transcript cũ thành event projection hoặc khẳng định vendor có atomicity này khi chưa có migration/adapter evidence. Native rewind/branching phải có view/event contract riêng; không sửa projection rows trực tiếp để rewrite execution history.

## 7. Timers và restart

Timer projection được dựng từ `TimerScheduled/TimerCancelled/TimerElapsed`. Scheduler chỉ đọc/re-arm timer và gửi command `TimerFired(timerID,generation,observedNow)` về coordinator. UTC deadlines và jitter đã được ghi; kernel không đọc clock hoặc random lại. Ngoại lệ run_deadline: active-window timer dùng trusted monotonic elapsed của cùng incarnation; recovery invalidate generation cũ, ghi unknown tail/reservation, không re-arm bằng thời gian wall đã trôi. Explicit resume mới conservative-charge outstanding tranche rồi mở window mới từ remaining budget theo state-machine §7.

Coordinator kiểm tra trusted clock input, generation, admission token cho admitted run hoặc queue-owner authority + run/session-queue revisions cho Queued run, target/purpose còn hợp lệ và command dedup. Quá sớm thì từ chối, timer cũ/cancelled thì no-op/conflict có receipt. UTC timer quá hạn sau restart có thể fire bằng đúng fence của state hiện tại; không bypass recovery_admission, vault, pause, budget hoặc current scope. Queued timer command không acquire/clear admission của run khác; v1 không schedule run_deadline cho Queued run.

Lifetime approval vẫn do owner xác nhận. Startup invalidates request/receipt/reservation cũ (kể cả request tạo trong Checking chưa được journal ghi nhận); không re-arm một approval cũ để người dùng trả lời lại. Timer để expiry không tự là authority giải quyết approval nếu owner chưa xác nhận.

Vault khởi tạo locked khi start, nhưng recovery MUST lấy snapshot/revision hiện tại từ vault owner qua subscribe + consistent read/catch-up. Recovery transaction lấy token mới luôn thêm `recovery_admission`, đồng bộ vault blocker theo observation: locked/unknown thì add/keep, unlocked thì clear blocker cũ với owner revision. Cùng batch classify dispatched attempts thiếu completion thành unknown/interrupted và invalidate time-window/check generations cũ. Không có scheduling trước khi catch-up/revalidate vault revision; stale observations bị từ chối và service vẫn check lock tại execute. Unknown thắng thành Interrupted nhưng giữ đúng wait reasons hiện tại; unlock không cấp resume authorization.

Recovery phân loại, không dùng một lệnh “mark all active interrupted”:

| Facts đã commit | Hành vi |
| --- | --- |
| `Queued`, chưa admitted | Giữ `Queued`; không dispatch |
| Chỉ intents `Planned/Checking/Ready` chưa `DispatchStarted` | Chưa có ambiguous tool effect; lấy ownership mới, thêm recovery_admission, đồng bộ vault state hiện tại; ToolCheckReset về Planned với generation mới |
| Tool `Checking/AwaitingApproval/Ready` | Read-back/ensure theo owner operation ID và check generation, invalidate request/receipt/reservation kể cả chưa có ToolApprovalRequested; ToolCheckReset + gỡ approval dependency cùng batch về Planned/generation mới; không project refused do restart hoặc hỏi lại trước unlock/resume |
| Chờ structured input | Owner invalidates token cũ; nhận observation, tạo request mới nếu hợp lệ |
| Attempt đã dispatch nhưng thiếu completion | Unknown/interrupted theo model/tool class; đối soát hoặc disposition riêng |
| Vault khóa nhưng dữ liệu còn | Block `vault_locked`; quiesce nếu cần; chờ unlock/revalidation |
| Protected payload mất/corrupt | Interruption payload_unavailable; không dùng dữ liệu rỗng; trusted user CloseRunWithoutPayload có metadata-only receipt/dispositions và clear đúng control admission khi finish |
| Schema không decode được | Host báo unavailable; không append hay đoán lifecycle của stream |

## 8. Unknown disposition và recovery theo class

`OutcomeUnknown` là fact, `UnknownAccepted`/`ToolAttemptAbandoned`/`RunClosureConfirmed` là disposition mới, không xóa fact cũ. User có thể chấp nhận đóng run bằng outcome `abandoned_unknown`; host policy có thể abandon pure-read/model attempt trong phạm vi contract để không khóa control progress vô hạn. Chi tiết ở [state machine](/dev-kit/core-harness/state-machine).

Disposition không có nghĩa external operation chưa xảy ra hoặc process đã dừng. Original invocation projection vẫn giữ `exposure=unknown`, result evidence và reconciliation status. Managed writer/resource owner tiếp tục giữ guards cần thiết; không tạo bảng exposure ledger thứ hai để thay owner.

Retry `idempotent` dùng cùng logical operation/input/key khi provider contract còn hiệu lực. Side-effecting unknown không auto retry. Unknown model usage tiếp tục reserve/đối soát budget, không ghi zero chỉ vì abandon response.

Run đã finished vẫn có thể nhận **reconciliation/accounting commands được allowlist** từ current owner để bổ sung evidence của attempt cũ. Không sửa outcome đã commit, transcript đã dùng, hoặc mở lại dispatch; thay đổi business disposition cần command mới có authority. Late worker callback thông thường vẫn bị fence.

## 9. Payload security, compatibility và client delivery

Event envelope SHOULD đủ để dựng control lifecycle không mở raw payload; **mọi native run muốn tiếp tục sau process start phải chờ người dùng mở vault** vì input, transcript và exact args nằm trong protected store, kể cả tool không dùng credential. Có thể dựng control view hoặc xử lý metadata-only cancellation khi khóa, nhưng không dựng provider context, recheck args hay AcceptUnknown preview. AcceptUnknown(close) thông thường yêu cầu unlock và exact protected preview, không dùng cached plaintext; CloseRunWithoutPayload là đường đóng metadata-only v1 khi không đọc được payload hoặc không mở được vault, theo guards/dispositions ở state-machine §6. Batch đóng không cần protected-store writes; không restore context, cập nhật contextRequirement trên admission row: missing/corrupt -> fresh_required, vault_locked -> revalidation_required; SelectRunContext giải quyết cùng admission run mới và không release external writer/resource ownership. Đây là UX activation gate G-03/G-07, không chỉ chi tiết storage. Không suy ra transcript/outbox hiện hữu đã encrypted: peer outbox có contract transcript-level plaintext riêng, không được nhân bản vào event metadata/logs.

Trước lưu payload thật phải chốt encryption-at-rest, bounded sizes, key lifecycle, deletion/export và backup trong G-03. Append-only không có nghĩa giữ dữ liệu nhạy cảm vĩnh viễn. Deletion có thể làm context replay không khả dụng; không hứa tái tạo model/world state từ metadata.

Event schema và execution protocol có version riêng. Unknown required event/protocol làm stream unavailable, không silently skip hoặc dùng projection cũ để chạy. Upcaster phải thuần; upgrade policy chọn drain/compatible resume/interruption. V1 không persisted snapshots; tính tương thích projection rebuild vẫn phải kiểm chứng.

Client lấy consistent projection view kèm sequence rồi catch-up events; không có khoảng trống snapshot/subscribe. Deltas có thể coalesce; durable control events không mất do UI backpressure. UI chậm không giữ transaction hoặc chặn cancellation. Security audit, execution journal và transcript có access/retention riêng; export ra ngoài cần explicit scope/redaction.
