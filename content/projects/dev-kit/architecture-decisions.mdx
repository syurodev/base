## ADR-001: Wails + React + Go core boundaries

**Status:** Accepted

**Decision:** DevKit dùng Wails v3 làm desktop shell, React/TypeScript cho UI,
và Go cho core services. UI chỉ gọi typed adapter trong `frontend/src/bridge/*`;
Go expose public surface qua `internal/bridge.AppService`; core logic nằm trong
`internal/services/*`, `internal/vault`, `internal/storage` — không import ngược
từ frontend generated bindings.

**Context:** Cần một desktop app cross-platform với offline-first UX, hot-reload
dev workflow, và security boundary rõ giữa UI untrusted-by-default và Go core
chứa crypto/vault/connection logic.

**Alternatives considered:**

- **Tauri + Rust core** — nhẹ hơn nhưng đòi hỏi rewrite toàn bộ service layer
  đã viết bằng Go.
- **Electron + Node backend** — ecosystem lớn nhưng memory footprint cao hơn và
  khó giữ crypto/key handling trong memory-safe Go path đã chọn.
- **Pure web app** — không đáp ứng local-first, file permission, và offline
  vault gate mà product yêu cầu.

**Consequences:**

- Positive: Một codebase Go cho vault, crypto, DB/SSH; Wails binding generation
  tự động; React ecosystem cho workbench UI.
- Negative: Phụ thuộc Wails v3 alpha APIs; cần maintain bridge adapter layer
  song song với generated bindings.
- Neutral: Server mode (`-tags server`) chia sẻ cùng Go core nhưng bỏ native
  window — boundary bridge/core vẫn giữ nguyên.

## ADR-002: Internal modules before external plugins

**Status:** Accepted

**Decision:** Phase đầu ship workbench modules (`notes`, `tools`, `database`,
`ssh`) như internal modules đăng ký qua `internal/modules.Registry` trong
`app.RegisterBuiltins`. Vault là core infrastructure — `Container.Vault`
(`internal/vault.Service`) và capability subject `builtin.vault` (`vault:manage`,
scope `vault`) trong container bootstrap — **không** phải entry trong module
registry. External plugin SDK, loader, marketplace và untrusted code execution
**không** ship cho đến khi Extension API và permission model được chứng minh ổn
định.

**Context:** `docs/architecture/devkit-architecture.md` principle #6 và #7: built-in
modules trước, security boundaries trước marketplace. Checkout hiện tại không
có `internal/plugins`, `internal/marketplace`, `internal/mcp`, `internal/sync`.

**Alternatives considered:**

- **Plugin-first platform** — nhanh hơn về extensibility nhưng tăng attack
  surface trước khi Capability Gateway và audit path mature.
- **Monolith không module registry** — đơn giản hơn nhưng khó mở rộng sang
  manifest/contribution model của Phase 2 roadmap.
- **Fork mỗi feature thành binary riêng** — trái product goal “một workspace
  thống nhất”.

**Consequences:**

- Positive: Toàn bộ sensitive path đi qua built-in subjects đã biết; policy
  container bootstrap cố định và testable.
- Negative: Third-party extension bị delay; cần refactor registry khi mở plugin
  surface.
- Neutral: Frontend `frontend/src/modules/registry.ts` mirror pattern nội bộ,
  chưa phải public Extension API.

## ADR-003: Capability Gateway as sensitive-call choke point

**Status:** Accepted

**Decision:** Mọi built-in operation nhạy cảm phải đi qua
`AppService.call(...)` → `capabilities.Gateway.Call(...)` với
`subject/capability/scope` check, metadata redaction, và audit trước khi handler
chạy. Core services không được expose trực tiếp cho UI hoặc future plugin
callers.

**Context:** Least-privilege principle và threat model yêu cầu một điểm kiểm soát
duy nhất cho authorization, audit, và redaction — tránh “bridge bypass” khi thêm
module mới.

**Alternatives considered:**

- **Per-service authorization** — phân tán policy, khó audit thống nhất và dễ
  miss check khi thêm endpoint.
- **UI-only permission gating** — không đủ; attacker hoặc bug có thể gọi thẳng
  bridge method.
- **Middleware trong Wails generated binding** — khó gắn scope opaque ID và
  metadata redaction theo từng operation family.

**Consequences:**

- Positive: Allowed/denied audit nhất quán; `recordID()`/`commandID()` opaque
  scope; tests cover deny path (`internal/capabilities/gateway_test.go`).
- Negative: `ListModules()` là ngoại lệ read-only không qua gate — cần review khi
  registry chứa metadata nhạy cảm.
- Neutral: Future MCP/plugin subjects cần grant model mở rộng trên cùng Gateway.

## ADR-004: Application-layer encrypted records instead of SQLCipher

**Status:** Accepted

**Decision:** SQLite (`devkit.db`) lưu JSON blob per record; secret fields được
mã hóa bằng vault DEK qua versioned crypto envelope **trước khi** persist.
Không dùng SQLCipher hay full-database encryption trong phase hiện tại. File
permission `0600`, `journal_mode=DELETE`, và `MaxOpenConns(1)` bổ sung defense
in depth.

**Context:** Local-first MVP cần encrypt credentials và note body mà không phụ
thuộc native SQLCipher build (cgo, cross-compile complexity). Nhiều metadata
(title, host, username) cố ý plaintext để search/list khi vault locked.

**Alternatives considered:**

- **SQLCipher full-DB encryption** — bảo vệ toàn file nhưng thêm cgo/native
  dependency và khó align với pure-Go `modernc.org/sqlite` driver đang dùng.
- **OS full-disk encryption only** — không bảo vệ khi vault unlocked hoặc
  process memory bị đọc.
- **Encrypt toàn bộ JSON blob** — phá search title và profile list UX hiện tại.

**Consequences:**

- Positive: Cross-platform build đơn giản; envelope versioning (V1/V2) độc lập
  với SQL schema; field-level encrypt/decrypt chỉ khi vault unlocked.
- Negative: `devkit.db` và plaintext metadata readable nếu attacker có file access
  khi vault locked — không phải zero plaintext at rest.
- Neutral: Có thể bổ sung SQLCipher hoặc field promotion sau nếu threat model
  yêu cầu, với migration plan riêng.

## ADR-005: V2-only envelope with AAD binding

**Status:** Accepted

**Decision:** Chỉ hỗ trợ envelope V2 với XChaCha20-Poly1305 và associated data
binding `record_type + NUL + record_id + NUL + key_id`. `SealV2` là đường ghi
duy nhất và `OpenWithAD` yêu cầu V2 cùng associated data matching. Envelope V1
bị từ chối với unsupported-version error.

**Context:** DevKit là greenfield và chưa có V1 ciphertext production cần bảo
tồn. Bỏ đường V1 làm giảm complexity và bảo đảm mọi encrypted record đều có
integrity binding chống swap ciphertext giữa records.

**Alternatives considered:**

- **V1 readability plus V2** — giữ backward compatibility nhưng duy trì đường
  giải mã không có record binding.
- **Mandatory migration job at startup** — đảm bảo V2-only nhưng tăng startup
  risk và phức tạp rollback.
- **V1 forever** — không có record binding; swap attack surface còn lại.

**Consequences:**

- Positive: Mọi service code (`notes`, `database`, `ssh`) đều ghi và đọc bằng
  V2 với AAD; API surface nhỏ hơn và không còn nil-AAD decrypt path.
- Negative: Nếu sau này phát hiện V1 ciphertext ngoài dự kiến, cần một migration
  tool được thiết kế và phê duyệt riêng.
- Neutral: Không có bulk re-encrypt flow vì không có V1 production data trong
  greenfield baseline.

## ADR-006: Loopback-only server mode

**Status:** Accepted

**Decision:** Build tag `server` tạo headless HTTP server chỉ bind loopback
(default `127.0.0.1`). `servermode.ValidateHost` reject public/wildcard
`WAILS_SERVER_HOST` tại startup. Không expose Docker port publishing cho server
mode.

**Context:** Server mode phục vụ dev/headless convenience (CI smoke, không GUI)
— không phải production remote API. Bind public mà chưa có TLS, authn, authz sẽ
tạo false sense of deployment readiness.

**Alternatives considered:**

- **Public bind + Wails defaults** — tiện demo nhưng expose bridge surface ra
  LAN/Internet không kiểm soát.
- **Separate authenticated API server ngay** — scope quá lớn cho MVP; trì hoãn
  đến thiết kế server riêng.
- **Disable server mode entirely** — mất headless test path hữu ích.

**Consequences:**

- Positive: Fail-fast nếu misconfigure host; README và `core-foundation.md` align
  messaging “not a remote API”.
- Negative: Không chạy server mode trong Docker container reachable từ host mà
  không weaken guard.
- Neutral: OS firewall/network policy vẫn là trách nhiệm operator — code chỉ
  enforce bind address tại startup.

## ADR-007: Verified TLS for remote DB and exact SSH host-key pinning

**Status:** Accepted

**Decision:**

1. **Database:** Remote PostgreSQL profiles default `sslmode=verify-full`. Chỉ
   cho phép `sslmode=disable` trên loopback dev hosts; remote + insecure TLS bị
   reject (`ErrInsecureTLSForRemoteHost`).
2. **SSH:** Connection chỉ thành công khi server host-key SHA-256 fingerprint
   khớp pin đã trust. Empty pin reject; changed key reject. TOFU flow qua
   `SSHObserveHostKey` → user approve → `SSHTrustHostKey`.

**Context:** Connection modules quản lý credentials đã decrypt từ vault — transport
security phải giảm MITM risk cho DB và SSH. Dev loopback exception giữ DX cho
local PostgreSQL/SSH test.

**Alternatives considered:**

- **Trust-on-first-use without persistence** — mỗi session hỏi lại; UX kém và dễ
  approve nhầm.
- **Trust system `known_hosts` globally** — không gắn với per-profile pin; khó
  audit trong app model.
- **DB TLS disable by default** — tiện dev nhưng nguy hiểm khi profile trỏ
  remote host.
- **Custom CA pinning cho DB** — chưa implement; hiện rely system CA store của
  pgx.

**Consequences:**

- Positive: Remote DB MITM protection mặc định; SSH MITM detected khi key thay
  đổi; tests cover reject paths.
- Negative: Manual host-key trust UX; DB custom CA pinning chưa có.
- Neutral: Passphrase SSH per-operation qua bridge — phụ thuộc redaction + UI
  discipline, không persist.

## ADR-008: Unified `vault_items` store for built-in item types

**Status:** Accepted

**Decision:** Gộp ba store riêng (`notes`, `connection_profiles`, `ssh_profiles`)
thành một bảng `vault_items` phía sau package chung `internal/services/vaultitem`
(`Record`, `Repository` memory + SQLite, và `Store` lo storage/crypto/search).
Notes/Database/SSH service trở thành thin adapter map field vào `metadata`
plaintext + `payload` mã hóa, giữ nguyên chữ ký public nên bridge/UI/capability
không đổi. Thêm bridge family `VaultSearch` với grant `builtin.search` /
`vault:search` / `item:search` cho search xuyên loại trên metadata.

**Context:** Ba module lặp lại cùng khuôn "vài field plaintext + một secret mã
hóa" nhưng mỗi cái có repository/crypto/search riêng, và không có nền chung cho
search xuyên loại, `key_version`, hay `sync_state` mà sync tương lai cần. Đây là
hạng mục Phase 1 "vault-item repository" mà roadmap đánh dấu là chặn giá trị
local-first.

**Alternatives considered:**

- **Generic CRUD + type registry hoàn toàn** — sạch nhất cho plugin-defined item
  type tương lai nhưng refactor lớn, mất type-safety và error/capability contract
  per-family; hợp Phase 2 hơn.
- **Chỉ unify bảng (một cột `type`, ba service giữ repository riêng)** — thay đổi
  nhỏ nhất nhưng không tạo được lớp chung, search vẫn per-service.
- **Giữ nguyên ba store** — không giao được giá trị vault-item repository.

**Consequences:**

- Positive: một nơi duy nhất lo storage/crypto/search; AAD binding per-type
  (`key_id` = `note-body`/`db-password`/`ssh-secret`) giữ nguyên chống swap; có
  `key_version`/`sync_state` làm nền sync; search xuyên loại chạy được khi vault
  khóa (chỉ đọc metadata).
- Negative: greenfield nên migration drop ba bảng cũ (m6) mà không backfill; nếu
  sau này có dữ liệu cần bảo toàn phải thêm migration riêng.
- Neutral: `record_type` cho DB profile đổi `database-profile` → `db-profile`;
  search hiện là substring trên metadata JSON, chưa có index trên cột `type`.
